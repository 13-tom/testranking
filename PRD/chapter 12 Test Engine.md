# Chapter 12 – Assessment Engine

## Phase 1 – Assessment Philosophy & Business Rules

**Project:** Board Ranking

**Document Type:** Product Requirement Document (PRD)

**Version:** 1.0

---

# 1. Introduction

The Assessment Engine is responsible for creating, delivering, managing, and evaluating every test conducted on Board Ranking.

Every test that a student attempts passes through this engine.

The Assessment Engine acts as the bridge between the Academic Question Management System (AQMS) and the Evaluation Engine.

Without the Assessment Engine, the Question Bank cannot be transformed into meaningful assessments.

---

# 2. Vision

The purpose of an assessment is not simply to generate marks.

The purpose is to measure learning.

Every assessment should:

* Evaluate knowledge.
* Identify strengths.
* Identify weaknesses.
* Encourage improvement.
* Produce fair rankings.

The Assessment Engine should support learning rather than memorization.

---

# 3. Core Objectives

The Assessment Engine must:

* Generate fair tests.
* Maintain academic balance.
* Prevent predictable question patterns.
* Support large numbers of students.
* Ensure every student receives an equivalent level of difficulty.
* Produce reliable data for rankings and analytics.

---

# 4. Assessment Philosophy

Board Ranking follows four principles.

### Fairness

Every student receives an academically equivalent assessment.

---

### Consistency

All tests follow standardized rules.

---

### Integrity

Students cannot manipulate the assessment process.

---

### Scalability

The engine must support millions of assessments without redesign.

---

### Ranked Mode

---

# 8. Assessment Principles

Every assessment must:

* Follow the blueprint.
* Use only published questions.
* Lock the question set after start.
* Maintain consistent difficulty.
* Preserve question versions.

---

# 9. Assessment Ownership

Assessments are created only by the platform.

Students cannot modify:

* Question count
* Difficulty
* Time limit
* Blueprint

The Assessment Engine succeeds if:

* The engine scales reliably.

The Question Selection Engine is responsible for selecting the most appropriate questions from the Academic Question Management System (AQMS).

Every assessment generated by Board Ranking depends on the quality of this engine.

---

# 2. Philosophy

A good assessment should:

* Cover the syllabus fairly.
* Maintain the required difficulty.
* Avoid repetition.
* Avoid predictable patterns.
* Measure multiple concepts.

Question selection is an academic process, not a database query.

✓ Published

✓ Latest Version

✓ Correct Curriculum

✓ Correct Class

✓ Correct Subject

✓ Correct Chapter

✓ Correct Topic

✓ Active Status

Questions failing any condition are ignored.

---

# 5. Difficulty Allocation

---

# 6. Chapter Allocation

Example

Chapter 1 → 5

Chapter 2 → 5

Chapter 3 → 5

Chapter 4 → 5

---

# 7. Topic Balancing

Within a chapter, questions should come from multiple topics whenever possible.

Example:

Chapter 5

Topic A

2 Questions

Topic B

---

# 8. Randomization Strategy

Randomization occurs only after all academic rules are satisfied.

The engine never sacrifices blueprint quality for randomness.

---

# 9. Fallback Strategy

If the required number of questions is unavailable:

Step 1

Use remaining questions from the same topic.

↓

Step 2

Expand to other topics within the same chapter.

↓

Step 3

Expand to the same subject while respecting blueprint rules.

↓

Step 4

Notify Admin if the blueprint cannot be satisfied.

The engine must never silently produce an invalid assessment.

---

# 10. Repeat Prevention

Release 1

If enough alternatives exist, avoid serving questions the student has attempted recently.

Future versions may use configurable lookback windows and adaptive repetition rules.

---

# 11. Question Diversity

The engine should avoid:

* Consecutive similar questions.
* Repeated concepts.
* Similar wording.
* Identical numerical values where avoidable.

Balanced variety improves assessment quality.

---

# 12. Quality Verification

Before the assessment is finalized, verify:

✓ Required question count

✓ Difficulty distribution

✓ Chapter distribution

✓ No duplicate questions

✓ Blueprint compliance

Only then may the assessment be generated.

---

# 13. Performance Goals

Target selection time:

Less than 1 second.

The engine should support thousands of concurrent assessment generations.

---

# 14. Business Rules

* Only Published questions are eligible.
* Every selected question must satisfy the blueprint.
* Duplicate questions are prohibited.
* Every assessment must pass quality verification before delivery.

Every attempt must be:

* Unique
* Traceable
* Secure
* Recoverable
* Reproducible

Each attempt represents one academic event.

## Phase 6 – Timer & Session Management Engine

**Project:** Board Ranking

**Document Type:** Product Requirement Document (PRD)

**Version:** 1.0

---

# 1. Introduction

The Timer & Session Management Engine is responsible for controlling the duration, validity, and continuity of every assessment attempt.

Its purpose is to ensure that every student receives the exact amount of time defined in the assessment blueprint while protecting the integrity of the examination.

The timer is managed entirely by the backend.

The frontend only displays the remaining time.

---

# 2. Objectives

The engine must:

* Start the timer accurately.
* Synchronize time with the backend.
* Prevent time manipulation.
* Handle browser refreshes.
* Support auto-save.
* Auto-submit when time expires.
* Maintain one active session per assessment attempt.

---

# 3. Timer Lifecycle

```text
Assessment Generated

↓

Student Clicks Start

↓

Backend Starts Timer

↓

Session Created

↓

Remaining Time Calculated

↓

Frontend Displays Timer

↓

Auto Save Runs

↓

Timer Reaches Zero

↓

Assessment Locked

↓

Auto Submit

↓

Evaluation Engine
```

---

# 4. Backend Timer Authority

The backend is the single source of truth.

The frontend:

* Cannot increase time.
* Cannot pause time.
* Cannot reset time.
* Cannot modify timestamps.

Every API request calculates remaining time using the backend clock.

---

# 5. Session Creation

When a student starts an assessment, the backend creates:

* Session ID
* Attempt ID
* Student ID
* Assessment Instance ID
* Start Timestamp
* Expected End Timestamp
* Session Status

Each session is unique.

---

# 6. Session Status

Allowed values:

* Active
* Paused (Reserved for future)
* Submitted
* Auto Submitted
* Expired
* Cancelled

Only one status may exist at a time.

---

# 7. Remaining Time Calculation

Remaining Time = End Time − Current Server Time

The server performs this calculation on every important request.

The browser timer is only a visual countdown.

---

# 8. Browser Refresh

If the student refreshes the page:

The system restores:

* Remaining Time
* Current Question
* Saved Answers
* Question States

The timer never resets.

---

# 9. Network Disconnection

If the internet disconnects temporarily:

* Timer continues on the server.
* Previously saved answers remain safe.
* Student resumes if time is still available.

No extra time is granted automatically.

---

# 10. Multiple Tabs

Release 1 Policy:

One active assessment session per attempt.

If another browser tab opens the same assessment:

* The existing session remains active.
* A warning is shown.
* Both tabs share the same remaining time.

Future versions may restrict multiple tabs more aggressively if required.

---

# 11. Auto Save

Auto Save occurs:

* After every answer selection.
* When navigating between questions.
* At regular background intervals (for example, every 30–60 seconds).

Auto Save never pauses the timer.

---

# 12. Auto Submit

When remaining time reaches zero:

The backend automatically:

* Saves pending answers.
* Locks the assessment.
* Updates status to Auto Submitted.
* Sends the attempt to the Evaluation Engine.

Students cannot continue after timeout.

---

# 13. Session Expiry

A session expires if:

* Assessment submitted.
* Timer expired.
* Assessment cancelled.
* Admin terminates the session (future).

Expired sessions become read-only.

---

# 14. Security Rules

Students cannot:

* Modify timer values.
* Extend assessment duration.
* Restart expired sessions.
* Change session IDs.
* Access another student's session.

Every session is protected using JWT authentication and server-side validation.

---

# 15. Error Recovery

If the backend becomes temporarily unavailable:

* Preserve the latest saved answers.
* Restore the session after recovery.
* Record the incident in audit logs.

Data integrity always has priority.

---

# 16. Performance Targets

Session creation:

Under 500 milliseconds.

Timer synchronization:

Under 100 milliseconds.

Auto Save:

Less than 300 milliseconds.

The system should support thousands of simultaneous active sessions.

---

# 17. Business Rules

* One active session per assessment attempt.
* Timer is managed only by the backend.
* Auto Save is mandatory.
* Auto Submit is mandatory.
* Submitted sessions cannot be reopened.

---

# 18. Success Criteria

The Timer & Session Management Engine succeeds if:

* Every student receives the correct amount of time.
* No progress is lost due to refreshes.
* Time manipulation is prevented.
* Auto submission is reliable.
* Sessions remain secure and consistent.

---

# CTO Final Statement

The Assessment Engine is the operational heart of Board Ranking.

It transforms academic content into meaningful assessments, preserves fairness through every student interaction, and provides the trusted foundation upon which evaluation, rankings, Study Points, and learning analytics are built.

Designed with modularity, security, and scalability in mind, this engine is capable of supporting the platform from its MVP to a nationwide educational ecosystem serving millions of learners.

The architecture intentionally separates content management (AQMS), assessment delivery (Assessment Engine), evaluation, rankings, and analytics into independent but connected systems.

This separation ensures that Board Ranking can evolve over the coming years without sacrificing reliability, maintainability, or academic integrity.
